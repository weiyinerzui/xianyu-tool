# 类型化选品 v0.5.0 开发计划（方案 v2）

> 状态：**待用户确认**（3 个决策点见 §11）
> 前置：v0.4.0 P0/P1 已完成——登录/采集/想要数链路端到端验证通过（103 tests）
> 本文档取代此前口头方案 v1（类型种子词库 + cCatId 聚合）

## 0. 需求锚点（不可漂移）

用户原始诉求：
1. **不预设关键词**，按商品类型（虚拟商品/卡券/教程等）发现
2. 类型内筛出**销量高、流量大、曝光量高**的商品
3. 全局三需求：选品 / 违禁词检测 / 曝光提升

## 1. v1 方案评议

### 1.1 站得住的部分
- cCatId 作为聚合维度：平台客观类目 > 人工关键词
- 类型间横向对比：选品的本质是机会比较
- 词库自进化意识

### 1.2 致命缺陷（v2 必须解决）

| # | 缺陷 | 后果 |
|---|------|------|
| 1 | "不预设"被偷换成"开发者预设"——内置词库仍是静态快照 | 回答不了"当下什么在涨" |
| 2 | 想要数被静默当成销量，未声明代理属性 | 结论虚高，误导决策 |
| 3 | 曝光维度完全缺失（原始需求③只字未提） | 三大需求只答了一个半 |
| 4 | cCatId 未验证就当地基：只有 ID 没有名字映射，覆盖率/粒度未知 | 聚合层建在沙上 |
| 5 | 吞吐矛盾：6 类 × 30 词 = 180 次采集，L2 每次弹浏览器 1-2 分钟 | 3-6 小时且必然触发风控 |
| 6 | 循环偏差：只爬种子词，没选的类型永远不可见 | "发现"是假的 |
| 7 | 卖家视角缺失：输出商品列表而非机会判断 | 不回答"该不该进这个类型" |
| 8 | 词库维护主体未定：180 个词靠人更新，三周必烂 | 静态词库不可持续 |

## 2. 关键技术事实（本轮调研已验证）

| 事实 | 证据 | 对方案的意义 |
|------|------|-------------|
| 详情 API `mtop.taobao.idle.pc.detail` 返回 wantCnt / collectCnt / **browseCnt** | goofish-cli `item/view.py` 提取器（data.itemDO 三字段） | **浏览数 = 流量/曝光代理**，需求③的数据基础。⚠️ 参考仓库证据可能过时（wantNum 教训：fixture 有值、实测为 0），**必须实测** |
| 搜索响应自带 index/position（排名）、seller_id、publishTime、cCatId/tbCatId/catId | 用户机器真实响应 dump（clickParam.args） | 排名位次 = 曝光代理②；卖家去重 = 竞争指数原料；全部免费，只需入库 |
| 无类目浏览 API，搜索强制 keyword | 6 个参考仓库全量检索 | "零预设"只能靠发现引擎，没有类目 Feed 可走 |
| L2 DOM 想要数回填已端到端验证 | 用户实测：30 条 + 19 回填（want=303/90） | **want_count 不依赖详情 API**；详情 API 的独特价值 = 浏览/收藏 |
| **DOM 想要数与已捕获 API 响应不一致**：同一次会话里 mtop 响应 wantNum 全 '0'，DOM 卡片却渲染真实值（514/297/…） | 用户 L2 诊断双源对比输出 | **页面从另一条未捕获通路获取想要数**（批量接口 / SSR / 其他 mtop）——找到它即可 L1 直取想要数，彻底绕开浏览器。S0.1 第一优先级 |
| Product 表已有 keyword 列；Snapshot 表已建成 | app/models/product.py | 跨词覆盖度、类型级动能的数据底座已在 |
| 旧上游搜索 API 曾直接返回 wantCount/viewCount | 旧版 httpx_crawler（awesome.post.search，现已失效） | 平台数据模型有这些字段，只是迁移到了详情 API——佐证详情 API 探针值得做 |

## 3. v2 架构：漏斗 + 双通道（L1 主干，L2 兜底）

```
发现层（宽、浅，L1 httpx——不弹浏览器）
──────────────────────────────────────
多源词（平台信号 + 种子 + n-gram）
   │
   ▼
L1 搜索 → 候选池入库：cCatId / 排名位次 / 卖家 / 发布时间
（此层不追求想要数：排名位次本身就是平台质量信号，
  用于入围筛选；想要数推迟到深化层统一获取）
   │
   ▼ 入围名单（每类型 Top-K，K≈20-40，按排名位次 + 新近度）
深化层（窄、深，详情 API / S0.1 待发现数据源）
──────────────────────────────────────
详情 API（或 S0.1 找到的批量源）：
wantCnt / collectCnt / browseCnt —— 一次请求三个代理指标全拿
   │
   ▼
类型聚合 → 三指数 → 类型机会报告 + 类型内 Top 榜
```

分工原则（不重复造轮子）：
- **宽层结构性字段**（cCatId / 排名 / 卖家 / 发布时间）→ 搜索响应直接入库，零成本
- **want / browse / collect** → 深化层统一获取（详情 API 或 S0.1 发现的批量源），只对入围名单调（控吞吐）
- **L2 DOM 回填**（已建成并验证）→ 降级为兜底路径：仅当 S0.1 NO-GO 时作为深化层替代
- **架构收益**：宽层彻底摆脱浏览器 → 吞吐从"每天几十词"解锁到"每天成百上千词"，多源发现与跨词曝光代理（需求③）从"做不起"变成"做得起"

## 4. Phase 0：数据探针（半天，GO/NO-GO）

| 探针 | 内容 | 产出 | NO-GO 后果 |
|------|------|------|-----------|
| S0.1 数据源（最高优先级） | ① L2 打开搜索页，记录**全部** XHR/fetch 请求，定位 DOM"N人想要"的真实数据源（已证实与搜索 API 响应不一致，必有未捕获通路）；② 实测详情 API 三字段 + 单次耗时 + 连续 20 次风控反应；③ 搜索页 HTML 是否 SSR 内嵌数据 | want/browse/collect 最优通路 + 字段清单 + 安全频次 | 深化层降级为 L2 详情页 DOM 提取；宽层维持 L2 DOM 模式（吞吐受限，类型轮采） |
| S0.2 cCatId | 3-5 个差异词采集，dump cCatId/tbCatId 分布 | 覆盖率/粒度报告 + 名字映射策略 | 聚合退化为用户桶（标题规则），cCatId 仅辅助 |
| S0.3 发现入口 | ① 搜索联想/热搜词（L2 输入字符抓包）；② 他人店铺货架（personal?userId= 是否有公开列表 API）；③ 相似宝贝推荐（详情页"相关推荐/看了又看"，从热点商品图扩散） | 可用信号源清单 | 发现退化为种子库 + n-gram（保底可行） |
| S0.4 风控基线 | 并入 S0.1/S0.3 实测 | 单位时间安全请求数 | 调整漏斗各层配额 |

探针全部在用户 Windows 机跑（需登录态），脚本由维护方写好推送，用户执行后回贴输出。

**Phase 0 出口**：四探针数据报告 + GO/NO-GO 决策 + 用真实数据生成一份**小样本类型报告**给用户过目——预期对齐后才开工 Phase 1+（避免建错方向）。

## 5. Phase 1：多源发现引擎

- **1.1 平台信号**（视 S0.3 结果）：搜索联想词 → 当下热词（零预设来源）
- **1.2 种子词库 v1**：6 类型 × 20-40 词，UI 标注"人工种子 · 非全集"
- **1.3 n-gram 自动扩词**：已采标题 → 高频 2-4 gram → 新种子提案（人工确认后入库）——打破种子边界的关键机制，数据驱动

## 6. Phase 2：数据模型扩展

- Product 增列：`c_cat_id` / `tb_cat_id` / `seller_id` / `rank_position`（入库时从 clickParam.args 提取）
- 跨词覆盖：新表 `product_keyword(xianyu_id, keyword, rank, first_seen, last_seen)`——现 keyword 单列无法表达多词命中
- Snapshot 增列：`browse_cnt`（S0.1 通过后）
- 存量数据不回填，标注"自 v0.5 起采"

## 7. Phase 3：评分与报告

三指数（**全部标注代理属性，不冒充真实成交/曝光**）：
- 需求指数 = median(想要数) 归一 + mean(想要数/上架天数)
- 竞争指数 = 上架数 + 卖家去重数 + 新品占比（30 天内）+ Top10 发布时间分布（老品霸榜 = 饱和）
- 曝光代理 = median(browseCnt) + 跨词覆盖度 + 平均排名位次
- **供给缺口 = 需求 − 竞争**（类型间排序主键）
- 类型动能 = 快照表类型级想要数增速（在涨还是在退）

交付物：
- **类型机会报告**：每类型一卡（三指数 / 价格带 / 供给缺口 / 合规风险 / 类目建议）
- **类型内 Top 商品榜**（回答"该类型内具体卖什么"）
- 样本 < 30 一律标"数据不足"，不出结论（宁可显式失败）

## 8. Phase 4：需求②③联动

- 违禁词：类型卡带合规风险等级（卡券/代做标红，软件激活标黄）
- 曝光：cCatId 选择 + 关键词覆盖 → 沉淀为上架打法（选对类目 = 拿对曝光池）

## 9. 风险与对策

| 风险 | 概率 | 对策 |
|------|------|------|
| 详情 API 字段已剥离（wantNum 前车之鉴） | 中 | S0.1 先行；NO-GO 走 L2 详情页 DOM |
| 风控触发 | 中 | 漏斗控量 + guard 限流 + 类型轮采（不同类型不同天）+ 单词日采 ≤ 2 次 |
| cCatId 无名字 / 粒度不可用 | 中 | S0.2 先行；退化用户桶 |
| 联想词接口不存在或加密 | 低-中 | 退化为种子 + n-gram（保底可行） |
| 样本偏差（搜索排序本身有偏） | 必然 | 报告标注"基于搜索可见性"；多词交叉降低单词偏差 |

## 10. 验收标准

- Phase 0：四探针数据报告 + GO/NO-GO 决策记录 + 小样本类型报告经用户确认
- Phase 1：词来源可解释、可禁用；n-gram 提案人工抽检准确率 > 50%
- Phase 2：新列入库率 100%（采到即有）；跨词覆盖表可查
- Phase 3：报告页可用；样本不足显式提示；同数据重跑排序一致
- Phase 4：合规等级显示在类型卡；曝光打法文档落地
